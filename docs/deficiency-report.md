# Assignment 1 deficiency resolution report

Part A lists every issue raised in the instructor's Assignment 1 marking, in the order of the
marking guide, and how it was corrected. Part B lists further problems found by reviewing the
Assignment 1 code while migrating it. Every resolution is in the Assignment 2 code.

## Part A: Issues from the instructor's Assignment 1 marking

| # | Issue (marking criterion) | Original problem | Resolution |
|---|---|---|---|
| A1 | Database design | The seed data created positions and candidates only for Pitt Meadows. | `SeedData.cs` seeds five municipalities (Burnaby, Surrey, Richmond, Pitt Meadows, Maple Ridge). Each has a Mayor, Councillor and School Trustee position, candidates for every position (39 in total) and its own Municipality Administrator account. |
| A2 | Database design | The database configuration fell back to a default connection string instead of requiring the configured one. | No project contains a connection string, and there is no fallback. `AddMemsData` throws a clear error if `ConnectionStrings:memsdb` is missing. The connection string is supplied only by .NET Aspire (`WithReference(database)` in the AppHost). The design-time factory used by `dotnet ef migrations add` builds the model only and never connects. |
| A3 | Authentication & authorization | Municipality administrators shared one role instead of having distinct municipality-specific groups. | Each municipality has its own administrator group: `AspNetUsers.MunicipalityId` is a foreign key to the municipality (`Municipality.Administrators`), so a Municipality Administrator belongs to exactly one municipality's group. Membership is issued as `tenant_id` / `tenant_slug` claims in both the admin cookie and the API token, and enforced by EF Core query filters, the API `TenantAdmin` policy and the service layer. Each municipality's details page lists its administrators. The group is tied to the municipality's id, not its name, so renaming a municipality cannot break access. |
| A4 | Authentication & authorization | Startup reset the seeded users' passwords to the default credential. | The seeder creates an account only if it does not exist and never changes an existing account, so a changed password survives every restart. The initial password `P@$$w0rd` is the one the instructor specified in Assignment 1, so it is kept for marking. It is no longer in the seeding code: it is the default value of the Aspire parameter `seed-admin-password` in `src/MEMS.AppHost/appsettings.json`, which can be overridden in user secrets without a code change. |
| A5 | Authentication & authorization (-3) | When a new municipality was created, there was no way to create an administrator for it. | After a Super Admin creates a municipality, the app opens its details page with the prompt "Next, add positions and an administrator". **+ Add administrator** opens the account form with that municipality already selected. Super Admins can also reset administrator passwords and remove administrators. |
| A6 | Candidate management | Upload validation checked the file extension and size but not the actual image content. | `ImageInspector` checks the file signature (magic bytes) and accepts only real JPEG, PNG, GIF and WEBP files. The check runs in the Blazor image picker and again in the service layer for every caller (Admin app and API). The stored content type comes from the detected signature, not from the file name or the browser. Size is checked before the file is buffered, and a SQL Server CHECK constraint caps images at 5 MB. |
| A7 | Candidate management | Uploads were stored under `wwwroot`, which risks losing them on redeployment. | Images are stored in SQL Server (`Images` table) as tenant-owned rows, and served by the API (`/api/{tenant}/images/{id}`) and the Admin app. Nothing is written to the web root, so a redeployment cannot lose them. An image is deleted in the same transaction as the record that owns it. |
| A8 | Candidate management (-3) | The Pitt Meadows administrator could see other municipalities and their candidates. | Every tenant-owned entity has an EF Core global query filter on its `MunicipalityId`. A Municipality Administrator's lists, details pages, dashboard totals and position drop-downs therefore contain only their own municipality. Another municipality's record is reported as "not found", and an API write to another tenant's URL returns 403. The `pm` account (Pitt Meadows) is still seeded to show this. |
| A9 | Voting guide (-2) | Administrators had the option to shortlist candidates. | The public site is now a separate, anonymous Blazor WebAssembly app with no sign-in, and the Admin app has no voting guide, so administrators cannot shortlist candidates. |
| A10 | Voting guide (-2) | A visitor could choose candidates from multiple cities in one guide. | A voting guide belongs to one municipality. It is stored under `mems.ballot.{slug}` and can be filled only from that municipality's pages, which read only that tenant's candidates from the API. Choices made in Burnaby can never be mixed into Surrey's guide. |
| A11 | Voting guide (-2) | A visitor could choose more than one mayor. | Each position allows at most as many choices as it has seats: one Mayor, and up to the number of Councillor and School Trustee seats. `VotingGuide.GetBlockReason` enforces this, the "Add to guide" button is disabled at the limit with an explanation, and the guide page shows a seat meter for each position. |
| A12 | User interface & usability (-2) | The UI was very simple. | Both sites were redesigned with Bootstrap 5. On the public site, each municipality has its own branding (logo, theme colour, tagline and election-day header), with candidate cards with photographs, per-position seat meters in the guide, and side-by-side comparison. The admin site has dashboard statistic cards, image previews, confirmation dialogs, inline validation messages and success/error notices. Both sites are responsive (see the mobile screenshots) and keep dark mode. |
| A13 | Azure deployment | The deployment URL did not respond, so live operation could not be verified. | Not applicable to Assignment 2, which states that no Azure deployment is required. The readme no longer lists a deployment URL. The whole system starts locally with one command (`dotnet run --project src/MEMS.AppHost` or `scripts/run.sh`), and the documentation includes screenshots of the running system in the Aspire dashboard. |
| A14 | Code quality, configuration & submission | No PDF/Word documentation with the ERD, screenshots, deployment evidence and repository URL was found. | `docs/Assignment2-Documentation.pdf` contains the system architecture diagram, ERD, screenshots (Aspire dashboard, admin site, public site, API testing, SQL Server database), this report, the Copilot usage summary, and the repository URL on its cover page. Because nothing is deployed, the Aspire dashboard screenshots are the evidence that the system is running. |
| A15 | Login page (-3) | The login page contained unnecessary template content. | The default Identity UI is gone. The admin login page (`/admin/account/login`) contains only the sign-in form (username, password, Sign in) and a one-line note that accounts are created by a Super Admin. The "Use another service to log in" section and its Microsoft help link, and the "Forgot your password?", "Register as a new user" and "Resend email confirmation" links, were removed. |
| A16 | User registration (-3) | Users could register themselves; accounts should be created only by an administrator. | There is no Register page, no `AddDefaultUI()` and no registration endpoint in the API. Administrator accounts are created only by a Super Admin on the Super-Admin-only **Administrators** page (`/admin/users`). |

## Part B: Issues found by reviewing the Assignment 1 code

| # | Issue | Original problem (Assignment 1) | Resolution (Assignment 2) |
|---|---|---|---|
| B1 | Data integrity | A candidate's municipality was only implied through its position, and nothing in the database stopped a candidate being linked to a position of another municipality. | `Candidates.MunicipalityId` plus a composite foreign key `(PositionId, MunicipalityId) → Positions`. The database rejects a cross-tenant candidate. |
| B2 | Data integrity | Position edit (`_context.Update(position)` with a posted `MunicipalityId`) could move a position, and its candidates, to another municipality. | A position's municipality cannot be changed (`PositionService.UpdateAsync` updates only name and seats). A candidate can change position only within its own municipality. |
| B3 | Data integrity | No uniqueness for position names within a municipality, no range check on election dates, and no database-level constraints beyond lengths. | Unique index `(MunicipalityId, Name)` on positions. Unique `Slug` and `Name` on municipalities. CHECK constraints on slug format, theme colour, election date (2000–2100), seats (1–100) and image size. |
| B4 | Authorization design | Tenant access depended on per-municipality Identity roles named after the municipality (`"<Name> Admin"`), which were renamed when the municipality was renamed. A user could belong to several of these roles, and every controller action had to remember to call `MunicipalityAccessService`. | Two fixed roles (`SuperAdmin`, `MunicipalityAdmin`) and `AspNetUsers.MunicipalityId`, so a Municipality Administrator has exactly one tenant. Isolation is enforced centrally by EF Core global query filters that fail closed, then again in the API (`TenantResolutionMiddleware` + `TenantAdmin` policy) and in the service layer. |
| B5 | Security | Initial seed password hard-coded in `DbInitializer` source. Password policy was 6 characters with no complexity. | The seeder receives the password as an argument and contains no credential. The value comes from the Aspire parameter `seed-admin-password`. Its default, the instructor-specified `P@$$w0rd`, is in the AppHost's `appsettings.json` (see A4), and a different value can be set in user secrets. Policy is 8+ characters with upper, lower, digit and symbol. The JWT signing key is generated by Aspire and persisted to user secrets, so it is not in the repository. |
| B6 | Security | Sessions stayed valid after an account was deleted or its password reset (default 30-minute stamp validation). | Security stamp validated on every admin request. Blazor circuits revalidate every minute. A deleted or reset account is signed out immediately (verified manually). |
| B7 | Security | `[Url]` accepted `ftp://` links. | `[HttpUrl]` accepts only absolute `http`/`https` URLs, so `javascript:` and `data:` links are impossible, at every layer. |
| B8 | Election privacy | The voting guide was stored in server-side ASP.NET session state (distributed memory cache, 7-day idle timeout), so the server held every visitor's choices. | Selections live only in the browser's `sessionStorage`. They are never sent to the API or written to SQL Server, and the browser clears them when the session ends. |
| B9 | Broken / incomplete cleanup | Deleting a position removed its candidates by cascade but left their photo files on disk. Delete actions called `SaveChangesAsync` even when nothing was found. | Images are stored in SQL Server as tenant-owned rows and removed in the same transaction as their owner. Deletes return 404 when the record is not found. |
| B10 | Architecture | Uploaded images were written to a local folder, which another application (API, second instance) could not see. | `Images` table, served by the API (`/api/{tenant}/images/{id}`) and the Admin app through the same tenant boundary. Responses are cacheable because ids are immutable. |
| B11 | Error handling | Developer exception page in Development, MVC error view elsewhere, no central logging of unhandled errors. | `IExceptionHandler` + ProblemDetails in the API, `UseExceptionHandler` and a logging `ErrorBoundary` in both Blazor apps, structured logging exported to the Aspire dashboard, user-facing messages with a trace id only. |
| B12 | Validation | Validation lived in MVC model attributes only; anything that bypassed the form also bypassed most checks. | Three layers: DataAnnotations on shared contracts (Blazor client validation), the same rules re-run in the service layer for every caller (API and Admin), and EF Core / SQL Server constraints. |
| B13 | Usability | Municipality administrators saw a restricted public site when signed in, and could not use the voting guide. | The public site is a separate anonymous application. Administrators manage data in `/admin` only. |
| B14 | Code quality | Data access and authorization logic were spread across MVC controllers. | Service layer in `MEMS.Data` (`IMunicipalityService`, `IPositionService`, `ICandidateService`, `IAdminUserService`) returning `Result<T>`, shared by the API and the Admin app. |
| B15 | Database | SQLite. | SQL Server in an Aspire-managed container with a persistent volume. The connection string is supplied by Aspire. |
