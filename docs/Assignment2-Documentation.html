1. Overview

Assignment 1's single ASP.NET Core MVC application is now a multi-tenant, cloud-native .NET 10 solution orchestrated by .NET Aspire. Each municipality is a tenant identified by a URL slug (/burnaby, /surrey, /richmond). Tenants are rows of data, not applications: a Super Admin creates a new municipality in the admin site and its public site works at once.

2. System architecture

Request flow for /burnaby/candidates

  1. The browser loads MEMS.Public. The router matches /{Tenant}/candidates, so the tenant is burnaby.
  2. The app calls https+http://api/api/burnaby/candidates. Aspire service discovery resolves api from configuration that the AppHost writes into the WASM app's wwwroot/appsettings.json (a browser app has no environment variables).
  3. TenantResolutionMiddleware looks up the slug and restricts TenantContext to Burnaby. An unknown slug ends the request with 404.
  4. CandidateService queries db.Candidates. The global query filter adds WHERE MunicipalityId = 1. Changing the id in the URL to a Surrey candidate gives 404.

3. Multi-tenancy and isolation

LayerHow tenant isolation is enforced
Routing (public)Every public page lives under /{tenant}. TenantShell resolves the tenant through the API, applies its branding (logo, colour, tagline) and shows "Municipality not found" for unknown slugs. Ballots are stored per tenant (mems.ballot.{slug}).
API/api/{tenant}/… routes. The middleware resolves the tenant before authorization. The TenantAdmin policy requires a Super Admin, or a Municipality Administrator whose tenant_id claim matches the URL (otherwise 403). The tenant is never read from a request body.

IdentityMunicipalityAdmin users have exactly one MunicipalityId. The claims factory adds tenant_id/tenant_slug to the cookie and the JWT.

7. Election privacy and vote confidentiality

RequirementImplementation and evidence
Store ballot selections only in the browser session (Session Storage)VotingGuide reads and writes sessionStorage through JS interop (key mems.ballot.{slug}, value [{CandidateId, PositionId}]). Nothing is written to localStorage; only the dark-mode preference uses it.
Never write selections to SQL ServerNo entity or table exists for them (see the table list in section 9).
Never send selections to the APIThe guide page downloads the tenant's full candidate list and matches the stored ids in the browser. An automated test recorded every API request during a full guide session: 67 requests, all GET, none carrying selections.
Remove ballot data when the session endsBrowser session storage is discarded with the tab/session. Tested: a new browser session shows "0 candidates chosen".
Administrators cannot view individual selectionsThe server never receives them, so no admin page, log, trace or database can show them.

The Assignment 1 PDF export (QuestPDF on the server) was replaced by a print-optimised page ("Print or save as PDF"). Generating the PDF on the server would have meant sending the ballot to the server. The specification also mentions local storage for selections. Session storage was chosen because the privacy section requires the data to disappear when the session ends.

9. SQL Server and EF Core

  • SQL Server 2022 runs as an Aspire container resource with a persistent data volume (mems-sql-data). No project contains a connection string: Aspire injects ConnectionStrings__memsdb.
  • EF Core Code First with the InitialCreate migration. The API applies migrations and seeds on start-up, and the Admin app waits for the API to be healthy (WaitFor).
  • Service layer: IMunicipalityService, IPositionService, ICandidateService, IAdminUserService, IImageService, ITenantDirectory. All use IDbContextFactory (safe for Blazor Server concurrency) and return Result<T>.
  • Multi-statement deletes run in a transaction through the execution strategy, because the Aspire integration enables connection retries.

12. Logging, error handling and security

  • Structured logging with message templates (e.g. "Candidate {CandidateId} created in municipality {MunicipalityId}"), cross-tenant attempts logged as warnings, and sign-in success, failure and lockout events.
  • Global exception handling: API IExceptionHandler → ProblemDetails with a trace id; Admin UseExceptionHandler("/error") plus an ErrorBoundary that logs and offers "Try again"; Public ErrorBoundary, and API failures become "Election information could not be loaded right now".
  • Nothing sensitive is shown: no stack traces or SQL in any environment; Blazor DetailedErrors off; identical messages for unknown user and wrong password.
  • Cookies are HttpOnly, Secure and SameSite=Strict. Antiforgery protects sign-out. Security stamps are validated per request. The login endpoint is rate-limited. HTTPS is used throughout and CORS allows only the public site.
